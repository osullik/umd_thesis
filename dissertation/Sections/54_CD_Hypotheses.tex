\section{Develop Hypotheses}
\label{section:54-CD-Hypotheses}

Hypotheses link the the problem and phenomena characterization with domain information gathered in exploratory experiments to specify the inputs and expected outputs for the `grey-box' benchmark. 
For each hypothesis, we consider what system characteristic or bottleneck we want to stimulate and build a hypothesis about how to shape the \textit{input} to trigger an observable change in the \textit{output} compared to some \textit{baseline} of performance.

\noindent \textbf{Inputs.}
The \textit{size, shape} and \textit{community structure} of the input graph are the three parameters that we can vary to elicit observable responses from the system. 

\noindent \textbf{Outputs.}
The \textit{\ac{ETLT}, \ac{ExT}, \ac{BL}} and \textit{NMI} of the solution are the observable components of the output that we can use to interpret the effect of the impact \nrscomment{effect of the impact doesnt make sense- change impact to "variation in inputs"}. 

\noindent \textbf{Baseline.}
All hypotheses are developed relative to a baseline configuration of a single socket \ac{CPU}, representing the graph as an adjacency list and implementing a sequential single-shot algorithm on a small uniform random graph. \nrscomment{why is this the baseline? simplicity? standard setup in I and S? give some hint of why in  there}

Our `grey-box' approach stimulates three areas: \textit{hardware} to stress specific configurations, \textit{representation} to stress different methods of representing and operating on graphs, and \textit{implementation} to stress different algorithmic approaches.
As Section~\ref{section:11-introduction-to-problem} explains, there can be unexpected interactions as we combine hardware, representations, and approaches; detecting these interactions is one of the goals of hypotheses design.

\subsection{Stimulating Hardware}
The hardware configuration of a \ac{SUT} directly impacts processing efficiency. 
While some \nrscomment{"Changes" not improvements- saying an improvement will yield an improvement is redundant} improvements will yield a linear improvement, like increasing available \ac{RAM}, or increasing the memory bandwidth, other approaches like distributing computing~\cite{Beamer2015}, using multi-socket \ac{CPU} systems~\cite{Dhulipala2021}, using \ac{GPU}~\cite{Wang2016} or other specific hardware accelerators~\cite{Aananthakrishnan2020} can have more dramatic impacts on efficiency. 
From reviewing the literature on \gai benchmarking, \nrscomment{replace comma with 'and'} workload analysis (see: Section~\ref{section:33-literature-gai-bottlenecks}) and the results of our exploratory analysis (see: Section~\ref{section:53-CD-Exploration}), we know that the size of a graph (number of vertices), density of the graph (number of edges), and shape of the graph can cause bottlenecks in different hardware configurations. 
To stimulate these bottlenecks, we vary two parameters in the input graph, the vertex count and graph shape, and \nrscomment{"define the following hypotheses about the expected impact on benchmark efficiency outputs: "} observe the impact on benchmark efficiency outputs. 

\hyp{Distributed hardware approaches will have a longer \ac{ETL} time relative to the same input and implementation on the baseline system.}

\hyp{Distributed hardware approaches operating on scale-free input graphs will have a longer \ac{ExT} than they do on mesh input graphs of comparable size.}

\hyp{A distributed hardware implementation will have a longer \ac{ExT} than a shared-memory parallel implementation for the same input data.}

\hyp{\ac{GPU} and other \ac{GHA} hardware configurations will have a longer \ac{ETL} time relative to the same input data and implementation on the baseline system.}

\hyp{\ac{GPU} and other \ac{GHA} hardware configurations will fail as input graph sizes become larger than their on-chip memory.}

\hyp{\ac{GPU} will have longer \ac{ETL} time for scale-free input graphs than for mesh input graphs of the same size.}

\hyp{The effectiveness of each workload is independent of the hardware configuration used.}

\subsection{Stimulating Representations}
Representational choices about storage, abstraction, primitive operations, and programming models can directly impact the efficiency of a \ac{SUT}.
For example, prior work reviewing linear algebraic graph processing discussed in Sections~\ref{section:23-graph-representations} and~\ref{section:53-CD-Exploration} has shown that the cost of converting between the traditional and linear algebraic representation can increase \ac{ETL} time. 
Despite the linear algebraic efficiency gains, the \ac{ExT} of linear algebraic approaches for \ac{CD} is slower than a system operating with the \ac{GAS} processing model because of the transformation overheads~\cite{Low2020}. 
The baseline for representations is an uncompressed adjacency list-based representation (i.e., \ac{CSC}/\ac{CSR}).

\hyp{Linear Algebraic representations to \ac{CD} will have a longer \ac{ETL} time for the same input data than the baseline approach.}

\hyp{Compressed representations will have a longer \ac{ETL} and \ac{ExT} than baseline representations of the input data.}

\hyp{The effectiveness of each workload is independent of the representation used.}

\subsection{Stimulating Implementations}
Choices about algorithm implementation used to solve the task on the input dataset can impact a solution's efficiency and effectiveness. 
Approximate solutions will accept a less effective result for a more efficient one, and iterative or incremental solutions will improve over time, yielding interim results that are less effective but much faster than waiting for the result of a single-shot implementation.
Being able to handle static or dynamic graphs is also an essential distinction in evaluating implementations. 
The baseline for implementations is a sequential, single-shot algorithm for a static graph.

\hyp{The \ac{BL} of single-shot approaches will be equal to its \ac{ETL} plus \ac{ExT} for all inputs.}

\hyp{The effectiveness of all implementations will be lower for mesh input graphs than scale-free input graphs of the same size.}

\hyp{The effectiveness of an iterative or incremental implementation will improve monotonically over time as it converges to an optimal state.}

\hyp{The effectiveness of an approximate implementation will be lower than a single-shot `exact' approach on the same input data.}

\hyp{Dynamic inputs will cause \ac{ETL} time to approach \ac{ExT} in incremental implementations.}
