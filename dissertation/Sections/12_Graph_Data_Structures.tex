\textbf{Community Detection.}
The \textit{population segmentation} intelligence task can be characterized as a community detection problem in graph analytics. 
The community detection problem was formalized by Girvan and Newman~\cite{Girvan2002} and has become a mainstay of challenging graph processing problems. 
It has been variously defined as `[the task of detecting] \textit{a subgraph whose members are more tightly connected than the broader graph}'~\cite{Fortunato2007} and `[the task of detecting] \textit{cohesive subgroups in networks}'~\cite{Reichardt2006}.
While various approaches exist, \textit{Modularity Optimization} dominates. 
\textit{Modularity} is a measure of how well connected a graph is compared to a random graph. 
The task of optimizing modularity requires determining the optimal partitioning of a graph so that each of the partitions has its maximal possible modularity~\cite{Newman2004a}.
Unfortunately, modularity optimization has been proven strongly $NP$-Complete~\cite{Brandes2006}, so heuristic approaches must be employed unless $P=NP$.

The community detection problem can be simplified with the addition of external information like known community membership constraints on a subset of the vertices in the graph.

\textbf{Isomorphic Subgraph Matching}
Both the \textit{Counter Threat Finance}, \textit{Spatial Pattern Matching} and some implementations of \textit{Co-Traveler Discovery} intelligence problems can be characterized as isomorphic subgraph matching (SGM) problems. 
The graph isomorphism problem asks whether a query graph $Q$ and a reference graph $G$ are topologically identical~\cite{Corneil1970}.
The subgraph isomorphism problem is a special, more difficult case of graph isomorphism. 
Subgraph isomorphism asks whether a query graph $Q$ exists as a subgraph anywhere within the reference graph $G$~\cite{Cook1971} and is also $NP$-Complete~\cite{Bachl1999}.
Resultantly, most approaches to SGM use heuristic approaches. 
Simple approaches slowly explore the graph from a given starting vertex, adding nodes that match the query pattern until a constraint is violated and then backtracking to the last known `good' state. 
Backtracking approaches end up traversing a lot of edges in their approach and can lead to high numbers of memory accesses in large graphs as edges are traversed to vertices that do not share spatial locality in memory.
The subgraph isomorphism problem can be simplified with the addition of attribute information like vertex labels that allow for more aggressive pruning of the search space. 

\textbf{Reachability and Searching.}
The \textit{Link Analysis} and \textit{Kill Chain} use cases both can be characterized as a problem of \textit{Graph Search}, and the special case of \textit{Reachability}.
These search-based queries form the majority of queries performed by the I\&S community, asking the questions of \textit{`What is happening with this entity'} (neighborhood search) and \textit{`Is there a connection between these two entities'}~\cite{Regli2022a}.
They are also tractable problems, with graph searches being primitive operations that are among the first taught to computing students around the world. 

The neighborhood search is implemented with a \textit{Breadth First Search} (BFS) algorithm.
Most BFS implementations pick a start vertex and \textit{expand} it by adding all neighbors (vertices connected by edges) to a queue.
It then takes a vertex from the front of the queue, checks if it is the target of the search and if not \textit{expands} that vertex to the end of the queue.
BFS can be constrained with a depth limit and terminate after a given number of traversals.
The result of a depth-constrained search is the collection of vertices that form the neighborhood of interest in the \textit{`what is happening with this entity'} query.
The simple BFS search requires $\mathcal{O}(b^{d})$ time and $\mathcal{O}(b^{d})$ space to execute where $b$ is the branching factor (approximated with $\bar{K}_{out}$) and $d$ is the depth of the solution (how many steps to take)~\cite{Russell2021}. 

The reachability search can also be implemented with BFS but is commonly implemented with a \textit{Depth First Search} (DFS) to reduce memory consumption~\cite{Vukotic2015}.
DFS also begins with a start vertex, but instead of adding the expanded nodes to a queue, they are added to a stack. 
At each step, the vertex on top of the stack is checked to see if it is the target, and if not its expansion is added to the stack, continuing until the whole graph has been visited or the target is found.
The simple DFS search requires $\mathcal{O}(b^{b})$ time and $\mathcal{O}(bm)$ space to execute where $b$ is the branching factor and $m$ is the maximum depth of the search~\cite{Russell2021}. 

\textbf{Entity Resolution.}
The \textit{All Source Fusion} intelligence problem is largely concerned with generating and transforming collected data into usable information that can be analyzed to create intelligence. 
To that end, it is largely focused on deduplication, and so can be viewed as an instance of the \textit{entity resolution} problem.
The goal of entity resolution is to reconcile data references corresponding to the same real-world entity. 
It can be framed as a graph problem by using the references to an entity to ground entities by their relation to other entities. The logic is that possible co-referent entities will share many of the same links to other entities, so topological similarity can be leveraged in addition to attribute similarity.
In addition to this approach which uses \textit{graph clustering}~\cite{Bhattacharya2006}, other approaches have used\textit{graph embedding}~\cite{Obraczka2021} distance, \textit{neural}~\cite{Ebraheem2018} methods, and \textit{graph-theoretic approaches} to exploit topological and attribute information~\cite{Zhang2020} of static graphs to resolve entities.
Work on \textit{dynamic graphs} uses an \textit{incremental partitioning} algorithm to re-evaluate prior resolutions as new information is added to the graph~\cite{Tauer2019}.

\textit{Graph clustering} problems are $NP$-Hard, and heuristic approaches remain expensive~\cite{Schaeffer2007}. 
Popular graph embedding approaches like \textit{DeepWalk}~\cite{Perozzi2014} and \textit{Node2Vec}~\cite{Grover2016} run in $\mathcal{O}(|V|)$ and $\mathcal{O}(b^{2})$ (where $B$ is the \textit{branching factor}) respectively~\cite{Pimentel2019}, but then must be processed by a MLP or Random Forest classifier.
The graph-theoretic approach runs in $\mathcal{O}(|E|^{3})$, with the impact reduced by running graph clustering as a pre-processing step to `block' the graph into smaller subgraphs to reduce processing time.
All that is to say that entity resolution is heavily impacted by the size and density of the graph, and hardware acceleration may offer the best path to improving entity resolution in a time-constrained setting. 

\textbf{Co-movement discovery.}
The geospatial analysis required to identify persons and places of interest based on reported movement patterns can be characterized as a \textit{co-movement problem}. 
The co-movement problem aims to discover entities that move together in time and space. 
The graph-based approach to this problem builds a separate proximity graph at each time step and then uses \textit{graph clustering} to assign proximal entities to groups.
When entities share clusters across multiple timesteps they are said to be co-movers~\cite {Tritsarolis2021}.
As has been discussed above, graph clustering is typically $NP$-Hard and heuristic approaches are sensitive to the size and density of input graphs. 

\textbf{Graph Neural Networks.}
The \textit{Intelligence Analysis} tasks of \textit{missing link prediction} and \textit{anomaly detection} can be solved using \textit{Graph Neural Networks}. 
GNNs are a class of neural network that operates directly on the underlying structure of the graph. 
Once a GNN is \textit{trained} for a particular task, it can be used to make \textit{Inferences}.
There are typically two key operations that happen within a GNN at inference time. 
First, it \textit{Samples and Aggregates} the edges to develop an embedding representation of the node neighborhoods in the graph (the topological and attribute information). 
Second, it \textit{Combines} those with the learned network weights to generate the outputs that are used to make predictions about which nodes are anomalous or where a link is likely to be missing~\cite{Hamilton2017}
Early work in GCNs showed that they could operate linearly to the number of edges in the graph~\cite{Kipf2016}, but in general graphs above trivial size require the use of sampling and blocking techniques to reduce the computational complexity to an acceptable level~\cite{Hamilton2017}.

\label{section:126-processing-bottlenecks}

A \textit{bottleneck}, or \textit{system constraint} is any resource whose capacity is equal to or less than the demand placed on it~\cite{Goldratt2004}. 
To improve the overall performance of a system, we must identify the bottleneck, exploit that bottleneck to maximize performance with the resources at hand, subordinate the rest of the system to that bottleneck, improve the bottleneck and then re-evaluate the system to find the new bottleneck~\cite{Goldratt1990}.
This section reviews the prior work in identifying the bottlenecks known to occur during graph processing, setting the scene for the discussion of using hardware accelerators to \textit{exploit} and \textit{elevate} those constraints in section~\ref{section:13-Graph-Hardware-Acceleration}.

Graph processing began, as most computer science problems do, as a math problem--the K{\"o}nigsberg bridge problem--asking if the seven bridges of K{\"o}nigsberg could be traversed in a single trip without doubling back, ending back at the start point. 
Euler's answer to this problem is generally heralded as the birth of graph theory~\cite{Barnett2005}.
The early computational approaches to graph problems focused on sequential algorithms on single machines. 
The rise of the `big-data' era has seen graphs increase in size from the four vertexes and seven edges of the K{\"o}nigsberg bridge problem to billions or trillions of nodes and edges. 

The increased graph size has flow-on effects. 
Large graphs quickly became unable to fit in the memory of a single machine, and even where they could because of a powerful machine or a compressed graph representation, sequential algorithms were too slow to process the graph in a reasonable time. 
Distributed computing offered a promising path to \textit{elevate} the single machine capacity bottleneck, but problems of how to efficiently partition graphs and synchronize operations on those partitions for distributed processing imposed new constraints, with network bandwidth, network latency and stalled cycles waiting for synchronization degrading performance. 

As computing capacity increased, \textit{elevating} the memory bottleneck, shared memory parallelism for graph processing gained traction.
With viable shared-memory parallel solutions emerging, the focus of the research switched to improving the efficiency of programming frameworks and the processing itself to \textit{exploit} these gains. 
The large number of graph-processing frameworks that exist `to abstract the complexity of implementing complicated parallel graph applications' evidences the growing demand for graph processing. 
Realizing that the performance of most graph processing algorithms is dependent on the shape of the input data drove a wave of efforts to \textit{exploit} the interaction of the algorithm with the representation by re-ordering the graph as a pre-processing step, scheduling the order that vertices are ordered, and partitioning the graph so subgraphs can fit into cache. 

Deeper analysis shows that graph algorithms are almost universally memory-bound, except for some distributed implementations which are network-bound. 
The constraints are commonly attributed to memory bandwidth and memory latency emerging from poor exploitation of the cache hierarchy and pre-fetching optimizations by graphs on CPU-based single machines, and a high communication-computation ratio for parallel (distributed and shared-memory) implementations. 
Hardware acceleration is a natural step to \textit{elevate} both local and distributed approaches. 
Representing graphs as matrices can allow us to \textit{exploit} the significant memory bandwidth available on GPUs, though sparsity quickly becomes a problem for the efficiency of both representation and computation, as well as incurring overhead for copying the graph data from main memory to the much more limited on-chip GPU memory. 
Other approaches use FPGAs and ASICs to \textit{elevate} the computation bottlenecks in graph processing. 
However, to maximize efficiency, they need to be hand-tuned to both the distribution of the input graph and the algorithm being deployed on the system.

There is a particular emphasis on accelerating GNN hardware as a special case of graph processing made more difficult by the \textit{hybrid} execution patterns that include both the sparse, irregular memory accesses of graph processing and the dense, regular computation of neural networks.
Taken together we can see that the efficient \textit{general purpose} processing of graph data structures is an open problem despite decades of work to \textit{exploit} graph processing with algorithmic and data structure innovations and \textit{elevate} performance through parallelization and hardware acceleration. 
Estimates of commercially interesting graph sizes range up to $20$ Terabytes (TB)~\cite{Aananthakrishnan2020} and as datasets become larger, approaching the exa-scale, we are likely to see an increase in the demand for accelerated, distributed graph processing~\cite{Azad2021}.

The following sections summarize each of these advances in turn and highlight common themes in the limitations that are used to inform the benchmark framework presented in chapter~\ref{chapter:30-Graph-Hardware-Benchmarking}.


\subsubsection{Memory Bottlenecks}
\textbf{Graph Size and Shape.} 
The sizes of graphs have been increasing in the `big data' era, with estimates of uncompressed commercial graph sizes exceeding 20TB~\cite{Aananthakrishnan2020}.
Beyond the Input/Output (I/O) problems that `big data' graphs pose in the face of no universally accepted binary exchange format~\cite{Azad2021}, large graphs quickly became unable to fit in the memory of a single machine, and some algorithms scale poorly as graphs reach larger sizes~\cite{Hong2012}.
When graphs are unable to fit in memory, the choices become \textit{distributing} the computation, or \textit{compressing} the representation~\cite{Shun2015, Mccune2015}. 
Popular compressed representations like the CSR/CSC formats will become hyperspace when graph decomposition techniques are employed~\cite{Azad2021}, so more aggressive compression is required to make it a useful tactic.
Unfortunately, compression is not viable for sequential algorithms, as the encoding/decoding cost for the compressed representation tends to outweigh the benefit of the smaller representation~\cite{Shun2015}, forcing the use of parallel implementations to `hide' the cost.
Shared memory parallelism has proven able to represent and process graphs with over $3.5$ billion vertices and $128$ billion edges within $1$ TB of RAM~\cite{Dhulipala2021}, demonstrating its viability as an alternative to distributed parallelism. 
Together, the size and shape of the input graph, combined with the algorithm being executed has a significant impact on computing efficency~\cite{Fu2014, Osama2022}, and so different algorithmic approaches to the same problem may need to be used depending on if the graph is \textit{random, scale-free} or \textit{mesh}~\cite{Lenharth2016}.

\textbf{Memory Boundedness.}
Graph algorithms are widely understood to be \textit{memory bound}~\cite{Beamer2015}. 
They are \textit{Data Intensive} algorithms, rather than the \textit{Compute Intensive} algorithms that modern general-purpose and GPU-accelerated systems are optimized for~\cite{Dysart2016}.
A program is \textit{memory bound} when the processor is not fully utilized, typically because it is stalled waiting for data to be retrieved from memory.
The \textit{memory bandwidth} of a system is commonly identified as the source of memory-boundedness for both \textit{traversal} and \textit{computationally intensive} graph algorithms~\cite{Satish2014}.
Memory bandwidth is a pressure point because the large number of irregular memory accesses prevent the effective use of the cache hierarchy and because very little computation is performed on each vertex when loaded from memory~\cite{Ahn2015}.

\textbf{The Memory Hierarchy.} General-purpose architectures alleviate memory bandwidth constraints with the caching system in the memory hierarchy~\cite{Hennessy2019}.
Caches are under-utilized in graph processing systems because of irregular memory accesses, resulting in a high cache miss rate~\cite{Song2016} that has been measured as causing $60-80\%$ of cycles to stall waiting for memory accesses~\cite{Zhang2017}.
The ineffectiveness of pre-fetching data in graph processing puts additional pressure on the cache hierarchy.
Only small portions of each cache line contain the data needed for the next computation step, wasting much of the memory bandwidth that is used to load data into the cache~\cite{Ham2016, Mukkara2018, Aananthakrishnan2020}. 
The `wasted space' in the cache lines is because of a lack of \textit{spatial locality} in graph data structures, which is generally true for many graph types, but particularly \textit{mesh} graphs with large diameters and a low mean degree~\cite{Oguntebi2016, Ham2016}.

\textbf{Spatial Locality.} 
\textit{Spatial locality} is the idea that when data is needed for processing, data stored near it in memory is also likely to be needed for processing soon, and so proximal memory blocks can be pre-emptively fetched to the cache for quick access~\cite{Hennessy2019}.
In figure~\ref{figure:locality-simple}, the vertices are stored in memory in \textit{vertex-order}, that is, written to memory in the order they are created (irrespective of edges).
Assuming we can load a block of $3$ contiguous vertices at a time from memory to a simple single-level cache as an example, the impact that poor \textit{spatial locality} is evident.
In most BFS implementations, the vertices linked by outgoing edges from the source vertex (\textbf{A} for this example) are added to a queue, with each being processed in turn until the target vertex is found. 
So, for the graph in figure~\ref{figure:locality-simple}, we would load the first three vertices from memory (\textbf{A, B} and \textbf{C}) to the cache for quick retrieval. 
The first `expansion' of \textbf{A} enqueues the pointers to \textbf{B} and \textbf{F}.
\textbf{B} is already in the cache and the `cache hit' when it is dequeued for expansion means that the vertex is quickly retrieved, exploiting the spatial locality of \textbf{A} and \textbf{B} in this instance. 
The processer expands \textbf{B} to add the pointer to its neighbor \textbf{C} to the queue.
When it comes time to expand \textbf{F}, however, there is a `cache miss'.
\textbf{F} is not in the cache, so the processor must now wait for it to be loaded from main memory, incurring a penalty proportional to the latency of retrieving the vertex from main memory plus the time it takes to load the whole block given memory bandwidth constraints. 
For simplicity, let us now assume that we have loaded another $3$ vertices starting from \textbf{F} (\textbf{F, G, H}) to replace the content of the cache and expand \textbf{F}, adding its neighbor \textbf{D} to the queue. 
\textbf{C} is now at the front of the queue but has been bumped out of the cache by the load of (\textbf{F, G, H}) so the processor must wait again for \textbf{C} to be loaded from main memory before it can be expanded. 
The problem continues throughout the algorithm, effectively `chasing pointers' all over the main memory, the `irregular memory accesses' that cause so much difficulty in graph processing~\cite{Beamer2015}.
The `pointer chasing' behavior here happens because of the poor \textit{spatial locality} in this graph.
Put simply, the vertices that are close to each other in the graph topologically are not close to each other in memory. 
It also shows how only a small percentage of each cache line is used in each step, putting pressure on memory bandwidth to load the entire block with very little use of what is loaded. 
The irregular memory access problem is exacerbated in larger graphs, where it is more likely that the vertex list does not fit in the cache and will have to access the main memory to retrieve the data~\cite{Chung2012}, reflected empirically in a decreasing \textit{instructions per miss} rate on larger graphs~\cite{Beamer2015}.

\textbf{Temporal Locality.} 
There is, however, some natural locality in \textit{scale-free} graphs that can be readily exploited. 
Consider figure~\ref{figure:locality-simple} again. 
While it isn't a scale-free graph in any real sense, vertex \textbf{D} has a much higher \textit{degree} than the other vertices. 
To \textit{exploit} the \textit{temporal locality} the system should cache nodes with higher degrees, as they are the ones most likely to be required by a graph algorithm.
So in a scale-free graph where most of the edges are owned by few vertices, there is latent temporal locality~\cite{Beamer2015}.

\textbf{Memory Bandwidth Utilization.} 
Na\"{\i}ve `flat' parallel processing implementations exacerbate memory bandwidth issues and impose a scaling limit on the number of processors as they for limited memory bandwidth~\cite{Fu2014}.
The observation is more concretely characterized by a decay factor of $P^{\frac{1}{2}}$ where $P$ is the number of processors~\cite{Buluc2012} because of the unfavorable communication-computation ratio.
However, studies of memory bandwidth utilization in general show that around $95\%$ of production systems utilize less than one-third of their memory bandwidth~\cite{Kanev2015}.
Graph-specific studies indicate that the existing bandwidth is poorly utilized when the instruction window size cannot hold enough instructions to account for cache-missing instructions~\cite{Beamer2015}.
While experiments on GPUs have shown that \textit{elevating} the memory bandwidth can increase throughput~\cite{Wu2015} through brute-force alone, it is insufficient to just increase the bandwidth, and more sophisticated methods are needed. 

\textbf{Memory Latency \& Attributed Graphs.} 
Contributing to the memory bandwidth issue, memory latency has a significant negative impact on system throughput~\cite{Beamer2015}.
The lack of locality combined with the data intensity of graph operations results in the latency of memory accesses overwhelming even highly optimized pipelined architectures~\cite{Dysart2016}.
The latency problem is exacerbated by attributed graphs. 
It is common for the topological and attribute data of a graph to be stored separately in memory~\cite{Buluc2013}. 
Figure~\ref{figure:locality-attributed} expands on the example from figure~\ref{figure:locality-simple} by adding in vertex attributes. 
The attributes are stored at separate memory locations, with pointers from the topological vertex (memory positions $1-9$) to their respective attributes (memory positions $10-29$). 
Attributes consume more memory so more memory bandwidth is required to load them.
The heterogeneous data types being loaded in attributed graphs (like knowledge graphs) have been shown to inflict significant Dynamic Random Access Memory (DRAM) accesses and hence, increase latency and memory bandwidth pressure~\cite{Basak2019}.
To illustrate why, again consider a BFS that is searching for the `\textbf{Grape}' vertex. 
Each time a vertex is dequeued, its attribute must be retrieved from memory to see if it is the target vertex. 
In the worst case, this is a memory access each time a vertex is checked, or, if reducing the latency of the comparison by pre-fetching the attribute along with the vertex, the cache block of $3$ quickly becomes filled with the vertex plus its attribute, exacerbating the spatial locality problem.

Overall, the processing of a graph is highly dependent on the shape of its input data. 
\textit{Scale-free} graphs have better temporal locality than \textit{mesh} graphs, but both struggle with optimizing for spatial locality. 
Combined, the lack of spatial and temporal locality results in poor utilization of the memory hierarchy in the average case~\cite{Balaji2018}.
The ineffective use of the memory hierarchy is exacerbated by the increasing sizes of graphs, with the largest not fitting in the memory of a single machine, and a known negative correlation between graph size and cache utilization. 
Graph processing is memory-bound and finding ways to \textit{Exploit} and \textit{Elevate} remain important research priorities. 

\subsubsection{Communication Bottlenecks}
Parallel approaches to graph processing are essential to addressing the memory and computation bottlenecks, but they incur particularly nasty communication bottlenecks because of the poor \textit{Communication to Computation} ratio causing them to become network-bound when algorithms need to process the entire vertex list~\cite{Satish2014} or when the graph is sub-optimally partitioned between workers~\cite{Chen2019}.
It is seen as the primary bottleneck impeding the scaling of graphs processing to exa-scale~\cite{Azad2021}.
Communication bottlenecks are present in all parallel graph algorithm implementations, stemming from the need the irregular communication-computation patterns that manifest as a large number of main memory accesses in the shared-memory paradigm and the large volume of inter-processor messages in the distributed paradigm~\cite{Beamer2015}.
In general, message-passing is more expensive than memory accesses~\cite{Beamer2015} and given that very large graphs can be processed in shared-memory parallel environments~\cite{Beamer2015, Dhulipala2021}, the conventional wisdom is to avoid distributed processing. 
Further, parallel algorithms need to enforce coarse and fine-grain synchronization~\cite{Aananthakrishnan2020} which can impose additional delay as processors are forced to wait during unbalanced computation when there is high contention for shared vertices~\cite{Chen2019}.

\textbf{Architectures.}
Graph processing workloads have been shown to run poorly on general-purpose parallel processors because the computing patterns of graph processing do not reflect the conventional highly localized workloads they are optimized to support~\cite{Song2016, Kepner2016}.
Known issues involve incurring overhead when the parallel framework enforces explicit function calls to exchange data between worker nodes~\cite{Dysart2016} and that general-purpose instruction sets like $x86$ bloat the inter-processor traffic with instructions~\cite{Ham2016}. 
One of the common thrusts in the discussion of parallel graph processing architectures is that a domain-specific architecture is needed to achieve optimal performance. 


\subsubsection{Computation Bottlenecks}
While graph processing is typically memory-bound, there are computational bottlenecks that can occur 
Load-balancing is a key challenge, particularly when parallelizing graph processing and working with graphs with heavilily skewed degree distributions~\cite{Aananthakrishnan2020}.
The irregular structure of graphs makes it hard to predict what work needs to be completed before execution time.
For example, many graph algorithms iterate until convergence, however, the number of iterations required to converge individual vertices or subgraphs can vary significantly, blocking other workers while they wait for the over-loaded worker to finish~\cite{Ozdal2017}.

\textbf{Branching.}
Graph processing is challenging for traditional architectures~\cite{Dadu2021}.
In addition to the pre-fetching and cache issues already discussed, graphs can make \textit{branch-prediction} and \textit{out-of-order} processing optimizations ineffective. 
Graph applications heavily use branches because future processing depends heavily on the structure and order of the input data that cannot be known until input time.
The branching operations are data dependent, irregular and so are hard to predict which contributes to the underutilization of out-of-order processors~\cite{Aananthakrishnan2020}.
Luckily, the impact of memory bandwidth under-utilization and memory latency is so significant that the vast majority of the time the branch misprediction rate has no meaningful impact on computation time, because it is masked by stalled memory accesses~\cite{Beamer2015}.


\textbf{Adjacent Problems.}
Many of the computational problems are not from the graph processing itself, but from generating heuristics and optimizing approximate solutions. 
One option to mitigate the impact of poor spatial locality is to pre-process the graph and re-order the vertices in memory which can be computationally expensive and time-consuming~\cite{Balaji2018}
Another is to use vertex scheduling to determine the optimal order to visit vertices to maximize spatial locality. 
vertex scheduling can be offline or online, though online approaches are generally infeasible because of their computational cost~\cite{Mukkara2018}.
Another optimization that aims to reduce memory bandwidth consumption and latency is `cache-blocking' where the graph is decomposed to subgraphs that can fit into the available cache. 
Closely related is the idea of \textit{graph-partitioning} which seeks to optimize the division of the graph between worker nodes in a parallel setting so that there are minimal cross-worker dependencies~\cite{Balaji2018}.
As is discussed in section~\ref{section:124-general-characteristics}, optimal graph partitioning is $NP$-Complete.
But sub-optimal partitioning leads to load imbalance and contention between workers for high-degree vertices~\cite{Chen2019}.
So, heuristic approaches approximate the partitions.
These approaches can involve computationally expensive eigendecompositions~\cite{Ng2001}, or complex test-and-adjust approaches like the \textit{Kernighan-Lin} algorithm~\cite{Kernighan1970} among others.
The shape of the graph has a significant impact on the `hardness' of partitioning.
\textit{Scale-free} graphs with small diameters are very difficult to partition, whereas \textit{mesh} graphs with large diameters are more easily separable because of the reduced interdependence of nodes~\cite{Beamer2015}. 
Indeed, there is a reasonable assertion that the key to improving the effectiveness of graph processing algorithms may depend on finding algorithms that can efficiently partition graphs and process them as independent subgraphs including streaming and distributed partitioning techniques~\cite{Mccune2015}.


\subsubsection{Paralellism as a solution}
Beginning with distributed approaches, and growing to include shared-memory parallelism when single machines gained the memory capacity to support processing, parallel approaches to graph processing are essential to \textit{efficient} and \textit{effective} graph processing. 
It is particularly hampered by load imbalance, synchronization overheads and non-uniform memory accesses (NUMA)~\cite{Beamer2015}

\textbf{Data and Algorithm Dependence.}
Parallel algorithms are particularly sensitive to the shape of the input data. 
Highly skewed degree distributions with small diameters are difficult to partition effectively~\cite{Beamer2015, Wu2015}.
Algorithms that are \textit{compute intensive} like PageRank which need to process all of the vertices in each iteration suffer from poor locality, and the memory latency cannot be hidden because of the poor communication-computation ratio~\cite{Ahn2015}.  

\textbf{Parallel abstractions.}
In general, graph computations are difficult to parallelize using traditional approaches because of their irregular structure and poor communication-computation ratio~\cite{Buluc2011}.
Factors like skewed degree distributions of graphs, heterogeneity of input graph types (scale-free, random, mesh) and maintaining synchronization make developing correct and efficient algorithms very difficult~\cite{Hong2012, Ediger2013}.
The proliferation of parallel graph processing frameworks and \textit{Domain Specific Languages} (DSL) that aim to abstract away all the hard-to-implement parallel processing operations and builds in expert optimizations so that the end-user-developer doesn't have to~\cite{Nguyen2013, Dhulipala2017}.
A common approach is to decompose graph operations into a collection of \textit{primitive} or \textit{atomic} operations, and then combine those to compose the required algorithms for processing. 
Vertex-centric models~\cite{Mccune2015}, edge-centric models, linear-algebraic models~\cite{Mattson2013, Kepner2016, Buluc2011, Azad2021}, models that apply the \textit{Gather Apply Scatter} (GAS), or the \textit{Frontier} model~\cite{Wang2016} all provide an abstraction to facilitate more efficient parallel graph processing. 
However, the frameworks are limited, with certain classes of algorithms unable to be represented in their abstractions (e.g. SSSP or MST implementations that use priority queues in early linear-algebraic approaches~\cite{Buluc2011}, bucketing algorithms in \textit{frontier} based models~\cite{Dhulipala2017}), impacts on message passing speed and memory consumption~\cite{Wu2015}, and a general finding that an abstracted library does not perform as \textit{efficently} as a hand-tuned natively implemented algorithm optimized for the system and data it is being run on~\cite{Satish2014}.

\textbf{Distributed vs. Shared-Memory}
The tradeoffs between distributed and shared memory parallelism have been discussed extensively above, but the core of the tradeoff is that distributed systems incur a network bottleneck that does not impact shared-memory systems in return for accessing potentially greater memory and compute resources~\cite{Shun2013, Beamer2015}.
Shared memory systems can exacerbate the already limited memory bandwidth issues as more compute resources compete for the limited memory bandwidth~\cite{Shun2015}, and so does not scale with the number of additional compute nodes~\cite{Ahn2015,Kepner2016}.

\textbf{Data parallelism vs Amorphous Data Paralellism}.
Most general-purpose parallel computing frameworks were developed for data parallelism. 
Data parallelism allows the same operation to be performed on multiple data at the same time to increase efficiency. 
While some graph processing algorithms have data parallelism, many exhibit a more complex parallelism pattern called “amorphous” data-parallelism~\cite{Lenharth2016}.
\textit{Amorphous} data parallelism is a more flexible approach that can better handle irregularity in the shape of data, at the cost of being processed less efficiently by general-purpose hardware. 

\subsubsection{GPU Acceleration}
The use of GPUs to accelerate computation has seen enormous success in the deep learning community in recent years~\cite{Dally2021}.
GPUs have significantly more memory bandwidth than a standard CPU architecture and are optimized for dense, regular computations. 
The increased memory bandwidth allows them to \textit{brute-force} their way through some of the memory-boundedness of CPU-based implementations of algorithms~\cite{Aananthakrishnan2020}, but they have several notable drawbacks. 

\textbf{GPU Memory.}
GPUs use high-speed on-chip memory to accelerate their operations. 
As a result, the data that they are processing needs to fit in the on-chip memory, which is typically much smaller than the main memory of the host system. 
The limited memory capacity makes it infeasible for them to process large graphs as a single node~\cite{Aananthakrishnan2020}, meaning that they need to be used as part of a parallel processing framework and manage the associated baggage for parallel processing systems discussed above.
The limited memory availability makes it particularly difficult to implement algorithms with large intermediate representations, as they consume the available memory and fail~\cite{Sundaram2015}.
The memory issue is exacerbated by the `GPU Trick' of densifying the connectivity matrix for more efficient computation which can increase memory consumption by orders of magnitude. 
The sparsity of graphs can also interfere with the memory coalescing process that is critical to efficient GPU computation~\cite{Aananthakrishnan2020}.
As a result, GPU graph programming frameworks focus on how to manage the number of `active' vertices during a computation to reduce the demands on the memory~\cite{Wang2016}.
It also highlights the importance of efficient sparse representations, with the CSR representation effectively doubling the size of the graph that can be processed by the GPU compared to a sparse adjacency matrix representation~\cite{Liu2014}, which is why it is the favored data format for all BSP implemenations~\cite{Wu2015}.

It is also important to note that the host system must copy the data across to the GPU before it can be processed, so for the use of an accelerator to be beneficial the efficiency gain in execution time must outweigh the cost of the partitioning and data movement~\cite{Azad2021}.

\textbf{GPU Compute.}
GPU computing is optimized for dense-regular computations that heavily exploit data parallelism. 
Graph processing involves sparse-irregular computations that feature amorphous data parallelism.
The impact of input data shape is evident, with more regular degree distributions (like a mesh network) seeing throughput increase linearly as the mean degree increases, but falling sharply as dense, skewed distributions inflict load-balancing overheads~\cite{Wu2015}.
As a result, GPUs are not optimized for graph processing, struggling with irregular data accesses/control flow~\cite{Wang2016}.
The Bulk Synchronous Parallel (BSP) paradigm employed by most GPU programming frameworks correlates the number of atomic (primitive) operation invocations with the overall performance of the algorithm--approaches that minimize the work they do tend to perform better overall~\cite{Wu2015}.
The primary challenge when using GPUs to execute graph algorithms is workload distribution~\cite{Wang2016}.
The irregular processing patterns mean that the thread assignments for the GPU can't be known until execution time because of their dependence on the data. 
Thread assignment is a common step in GPU pre-processing and deferring to execution time degrades GPU performance relative to a typical dense, regular workload~\cite{Fu2014}.
Imbalance in the graph because of a skewed degree distribution exacerbates the unpredictability of load-balancing that comes from not being able to pre-assign the threads and can result in uncoalesced memory patterns, and thread divergence, severely hampering GPU performance relative to dense regular tasks~\cite{Fu2014}. 
In a distributed setting, branches cause thread divergence and synchronization overheads limit thread progress~\cite{Aananthakrishnan2020}.
