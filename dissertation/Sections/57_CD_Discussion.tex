\section{Discussion}
\label{section:57-CD-Discussion}
We make the following observations based on the results described in Section~\ref{section:56-CD-Results} and the context of the hypotheses stated in Section~\ref{section:54-CD-Hypotheses}.

\textbf{The NetworkX GPU is much faster across all data shapes.}
Execution time increases proportional to the size of the graph, approximately quadratically to the number of vertices across all implementations. 
Our datasets are mostly mesh graphs where the number of $|E|\rightarrow|V|$. 
The OSM-WA dataset is the most extensive mesh graph, yet the OSM-MD mesh graph takes the longest to complete.
Both have comparable edge densities, and the somewhat irregular shape of the state of Maryland likely yields a larger diameter, suggesting that the shape of the input graph has as much influence as the size. 
More experimentation is required with graphs of intermediate shapes between OSM-WA and OSM-MD to confirm this assessment.

While mesh graphs do not represent typical real-world community structures, it shows that the assertion that the Louvain algorithm and its derivatives are `near linear in practice~\cite{Blondel2008, Traag2019} is misleading.

\textbf{Execution time dominates, but ETL time is non-trivial for small graphs and \ac{GPU}s.}
Benchmarks typically focus on execution time because the execution phase is frequently the processing bottleneck, and the \ac{ETL} costs in static graph processing are assumed to be amortized over the life of the graph.
The results in Figure~\ref{Figure:proportions} show that for small graphs on \ac{CPU} based systems, \ac{ETL} can take up to $20\%$ of total experiment time, and for \ac{GPU} based systems, it can approach $75\%$ on larger graphs.
While the \ac{GPU} results in part, emphasize the processing phase's speed, it also highlights the overhead incurred with transforming data and copying it to an external accelerator.
We expect additional testing on larger datasets will show that \ac{GPU} approaches will fail as the size of the dataset exceeds the amount of memory available on the \ac{GPU}.
Further, ss we implement support for dynamic graphs involving many small \ac{ETL} activities over time, we expect \ac{ETL} to take more significant proportions of the total experiment runtime, which will exacerbate the \ac{ETL} overheads incurred by external accelerators as each timestep now has an ac{ETL} step and the cost is not hidden as effectively by the improvements in \ac{ExT}.

\textbf{The Louvain Partitions implementation does not yield incremental solutions.}
Reviewing the batch latency (Figure~\ref{sub@Figure:batch-latency}) shows that the NetworkX implementation of Louvain Partitions does not yield an answer after each partition.
Instead, it completes the algorithm and returns a generator containing all the partitions.
To effectively measure the `benefit' of an incremental solution through batch latency, an incremental algorithm must return results in real-time or significantly less than the total runtime of the algorithm.
Without returning results in real-time, they provide no real ability for a user to decide on thresholds for early-stopping in their system and remove the option to trade effectiveness for efficiency as an optimization tactic. 

\textbf{The Louvain Partition implementation behaves inconsistently between \ac{SUT}.}
One assumption about the benefit of an incremental or approximate approach to balancing effectiveness and efficiency is that it should improve monotonically. 
That is, the longer it runs, the better the solution gets. 
Figure~\ref{Figure:monotonics} shows erratic variation in the size of communities and the NMI at each step for the baseline \ac{SUT}, suggesting that we cannot make predictable trade-offs of efficiency and effectiveness on the baseline system.
The \ac{GPU} \ac{SUT} does not support the iterative louvain partition implementation. 
However, the \ac{CPU} \ac{SUT} exhibits the expected monotonic behavior, allowing users to trade-off between effectiveness and efficiency if the implementation is adjusted to output results in-stride, as an alternative approach to work within time constraints if a \ac{GPU} is too costly.

\textbf{Summary.}
Our small experiments show how the engineer can determine that the current baseline implementation has some issues with the effectiveness that warrant moving quickly to a different solution, that the \ac{GPU} will provide a significant speed-up on datasets at the tiny and small sizes, and that the NetworkX Louvain Partitions implementation must be updated to trade effectiveness for efficiency.
Knowing the empirical gains expected from procuring the hardware, the engineer can make an informed, data-driven decision about whether the cost of that hardware is justified for the use case.
For a fully-informed view, the engineer should repeat the benchmarking process with the respective \gai benchmark problems to understand the trade-offs using a \ac{GPU} based approach that may require another \gai tasks.
